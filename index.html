L1

Basics

One server, then a few. New problem: one machine can't handle the traffic.

0 / 10 done

What system design is

  • You turn a fuzzy goal into parts (boxes) and data paths (arrows).
  • Functional needs: what it does. "Users post photos."
  • Non-functional needs: how well. Latency, uptime, scale, cost.
  • No design is "right". Every choice trades one thing for another.
Rule: say the trade-off out loud.

Life of a request

  • DNS turns a name into an IP address.
  • TCP + TLS open a safe connection. This costs round trips.
  • HTTP carries the request. The server answers with a status code.
  • The server usually calls a database before it answers.
Every arrow here adds latency.

Latency numbers

  • Memory is about 1,000× faster than SSD.
  • A round trip inside one data center is cheap. A trip across an ocean is not.
  • Most design moves exist to swap a slow step for a fast one.
Cache in RAM. Keep data close to users.

Back-of-envelope math

  • Estimate load before you pick parts.
  • Round hard. 86,400 seconds a day ≈ 100k.
  • Peak traffic is often 2–5× the average.
10M users × 10 req = 100M req/day 100M ÷ 100k s = ~1,000 req/s avg peak ≈ 3 × avg = ~3,000 req/s 1 KB × 100M = 100 GB/day stored 100 GB × 365 = ~36 TB/year

Vertical vs horizontal scaling

  • Vertical: buy a bigger machine. Simple. Has a ceiling. One failure takes all.
  • Horizontal: add more machines. No ceiling. Needs a load balancer.
  • Horizontal works best when servers are stateless. Keep sessions in a shared store.
Stateless app servers + shared state store.

Load balancer

  • Spreads requests across servers.
  • Algorithms: round robin, least connections, hash by user or IP.
  • Health checks remove dead servers from the pool.
  • L4 routes by IP and port. L7 reads HTTP and routes by path or header.
  • Run two balancers, or the balancer becomes the new single point of failure.

Caching

  • Keep hot data in RAM (Redis, Memcached). Skip the slow database.
  • Cache-aside: app checks cache, then DB on a miss, then fills the cache.
  • TTL expires old entries. LRU evicts the least recently used when full.
  • Hard part: stale data. When the DB changes, delete or update the cache entry.
Hit rate is the number that matters.

CDN

  • A CDN is a cache for files, placed in many cities.
  • Images, video, JS and CSS load from the nearest edge.
  • The edge calls your origin server only on a miss.
  • Result: lower latency and much less load on your servers.

SQL vs NoSQL

  • SQL: tables, joins, ACID transactions. Postgres, MySQL.
  • NoSQL: key-value, document, wide-column, graph. Built for one access pattern at large scale.
  • Pick by access pattern, not by hype.
Default: Postgres. Switch only for a clear reason.

APIs and real-time

StyleUse it for
RESTPublic APIs. Resources + HTTP verbs.
GraphQLClients that pick exact fields.
gRPCFast service-to-service calls.
WebSocketChat, games, live updates.

L2

Mid

Scale the data, not only the servers. New problem: the database is now the bottleneck.

0 / 10 done

Replication

  • Keep copies of the same data on several machines.
  • Leader–follower: writes go to the leader. Followers copy it and serve reads.
  • Replication lag: a follower can be behind. You may read old data.
  • Failover: if the leader dies, promote a follower.
Scales reads. Does not scale writes.

Sharding

  • Split data across machines. Each shard holds a slice.
  • Hash sharding: even spread. Range queries get hard.
  • Range sharding: easy ranges. Risk of hot shards.
  • Hot key: one celebrity account can overload one shard.
  • Cross-shard joins and transactions get slow. Pick the shard key with care.
Scales writes. Costs joins.

Consistent hashing

  • Put nodes and keys on one ring.
  • A key belongs to the next node clockwise.
  • Add or remove a node: only its neighbor's keys move. About 1/N of keys.
  • Virtual nodes: each server takes many ring spots. Load evens out.
  • Used in DynamoDB, Cassandra, CDNs, cache clusters.

CAP theorem

  • Networks split. When they do, a node must choose.
  • CP: refuse to answer. Never wrong, sometimes down.
  • AP: answer with what it has. Always up, sometimes stale.
  • PACELC: with no split, you still trade latency (L) for consistency (C).
Banks lean CP. Like counters lean AP.

Message queues

  • Producers drop jobs in a queue. Workers pull them later.
  • Absorbs traffic spikes. The web request returns fast.
  • Decouples services. A slow worker does not block users.
  • Failed jobs retry, then go to a dead-letter queue.
  • Tools: SQS, RabbitMQ, Kafka.

Cache write strategies

StrategyOn writeRisk
Cache-asideWrite DB, delete keyShort stale window
Write-throughWrite cache and DBSlower writes
Write-backWrite cache, flush laterLoss if cache dies

Stampede: a hot key expires and thousands of requests hit the DB at once. Fix it with a lock, early refresh, or random TTLs.

Rate limiting

  • Caps requests per user, IP or API key.
  • Token bucket: tokens refill at a fixed rate. Each request takes one. Empty bucket means HTTP 429.
  • Bucket size sets the allowed burst.
  • Other options: fixed window, sliding window log, leaky bucket.
  • Shared limits across servers need a shared counter, often Redis.

Indexes

  • No index: the DB scans every row. 10M rows = slow.
  • B-tree index: 3–4 page reads find one row.
  • Each index speeds reads but slows writes and uses disk.
  • Composite index (a, b) helps queries on a, or a + b. Not b alone.
Index the columns in your WHERE and ORDER BY.

Monolith vs microservices

  • Monolith: one codebase, one deploy. Fast to start.
  • Microservices: small services, each with its own data. Teams ship alone.
  • Cost: network calls, partial failures, harder debugging.
  • An API gateway handles auth, routing and rate limits at the front door.
Start with a monolith. Split when teams block each other.

Interview framework

  • Ask before you draw. Who uses it? How many? Read-heavy or write-heavy?
  • Do quick math. It tells you which parts matter.
  • Draw a simple design that works. Then fix the bottleneck.
  • Close with trade-offs and what you would do next.

L3

Advanced

Look inside the data systems. New problem: copies disagree, retries double-charge, writes get lost.

0 / 10 done

Storage engines: B-tree vs LSM

  • B-tree: updates pages in place. Fast reads. Postgres, MySQL.
  • LSM-tree: appends only. Fast writes. RocksDB, Cassandra.
  • LSM writes go to a log and a RAM table, then flush to sorted files.
  • Background compaction merges files and drops old versions.
  • Bloom filters let reads skip files that cannot hold the key.
Write-heavy? LSM. Read-heavy? B-tree.

Consistency models

  • A consistency model is a promise about what reads can return.
  • Stronger promise = more coordination = more latency.
  • Many apps need only read-your-writes for the user's own data.
  • Pick per feature. A bank balance and a like counter need different promises.

Quorums

  • N copies. A write waits for W acks. A read asks R copies.
  • If W + R > N, every read set overlaps every write set.
  • The overlap copy holds the newest version. The reader keeps the newest.
  • Common setting: N=3, W=2, R=2. Survives one dead node.
  • Used in Dynamo-style stores: Cassandra, Riak, DynamoDB internals.

Isolation levels

LevelStopsStill allows
Read committedDirty readsLost updates
SnapshotChanging reads mid-txnWrite skew
SerializableAll of the aboveNothing; it costs speed

Many databases default to read committed. Check yours. Fix lost updates with atomic updates (SET n = n + 1), SELECT … FOR UPDATE, or serializable mode.

Two-phase commit (2PC)

  • One transaction across two databases. All commit or none.
  • Phase 1: coordinator asks "can you commit?" Each node locks and votes.
  • Phase 2: all YES → commit. Any NO → abort.
  • Weak spot: a dead coordinator leaves nodes stuck, holding locks.
Correct, but slow and blocking.

Sagas

  • Split a long process into local steps. Each step commits alone.
  • If a step fails, run compensating steps in reverse.
  • No global locks. Other users can see half-done states.
  • Orchestrated: one service drives the steps. Choreographed: services react to events.
Microservices use sagas, not 2PC.

Event logs (Kafka)

  • A topic is an append-only log, split into partitions.
  • Events keep their order inside one partition only. Key by user or order ID.
  • Each consumer group tracks its own offset. Many readers, one log.
  • Events stay for days. A new service can replay history.
Queue: a job is done once. Log: events are kept and replayed.

Idempotency

  • Networks drop replies. Clients retry. Retries can repeat side effects.
  • An idempotent operation gives the same result if run twice.
  • Client sends a unique idempotency key. Server stores key + result.
  • "Exactly once" in practice = at-least-once delivery + dedupe.
Every payment API needs this.

Outbox pattern and CDC

  • Dual-write bug: save to DB, then publish to Kafka. If step 2 fails, systems drift.
  • Outbox: write the row and the event in one DB transaction.
  • A relay reads the outbox table and publishes. It retries until it succeeds.
  • CDC (change data capture) reads the DB's own log. Tool: Debezium.

Observability and SLOs

  • Metrics tell you something is wrong. Traces show where. Logs show why.
  • SLI: what you measure, like p99 latency. SLO: the target. Error budget: allowed failure.
  • Watch p99, not the average. Averages hide slow users.

L4

Expert

Distributed systems theory. New problem: clocks drift, messages vanish, and nodes stop in the middle of a step.

0 / 9 done

Partial failure

  • One machine either works or crashes. A cluster can be half broken.
  • A timeout tells you nothing about the cause.
  • Failure models: crash-stop, crash-recovery, lost messages, slow nodes, lying nodes (Byzantine).
  • The network is not reliable, latency is not zero, and clocks are not in sync.
Design every call for "no answer".

Logical clocks

  • Wall clocks drift. NTP can jump them backward. "Last write wins" by timestamp can drop writes.
  • Lamport clock: a counter. +1 per event. On receive: max(mine, message) + 1.
  • If a caused b, then L(a) < L(b). The reverse is not true.
  • Vector clocks keep one counter per node. They detect concurrent events.

Linearizability

  • The system acts like one copy. Once a write finishes, every later read sees it.
  • Needed for locks, leader election, unique usernames, bank balances.
  • Linearizable is about one object in real time. Serializable is about transactions over many objects.
  • Both together = "strict serializable". Spanner gives this.

Consensus: Raft leader election

  • Consensus = nodes agree on one value, even when some crash.
  • Raft picks one leader per term. Terms only go up.
  • A follower that hears no heartbeat becomes a candidate and asks for votes.
  • Majority wins. 5 nodes survive 2 failures. 3 nodes survive 1.
  • Built on it: etcd, Consul, CockroachDB, Kafka KRaft.

Consensus: Raft log replication

  • The leader appends each command to its log and sends it to followers.
  • An entry is committed when a majority stores it.
  • Committed entries never change. All nodes apply them in the same order.
  • Same log + same order = same state machine. This is state machine replication.

Split brain and fencing tokens

  • A lock holder can pause (GC, VM freeze) and wake up after its lease expired.
  • It still thinks it holds the lock. Now two nodes act as leader.
  • Fix: the lock service hands out a number that always goes up, the fencing token.
  • Storage rejects any write with a token older than one it has seen.
Leases alone are not safe. Fence the writes.

TrueTime and Spanner

  • Google Spanner is a global SQL database with strict serializability.
  • TrueTime uses GPS and atomic clocks. It returns a time range, not one point.
  • On commit, Spanner picks the top of the range, then waits out the uncertainty.
  • After the wait, any later transaction gets a larger timestamp. Order is safe without talking.
Spend a few ms of waiting to buy global order.

Multi-region

  • Active–passive: one region writes, one waits. Simple. Failover can lose the last seconds.
  • Active–active: both regions write. Low latency everywhere. Conflicts appear.
  • Conflict fixes: last-write-wins, merge rules, CRDTs, or one "home region" per user.
  • A sync write across an ocean adds about 100 ms or more.

Tail latency at scale

  • One user request may fan out to 100 servers. It is as slow as the slowest one.
  • If each server is slow 1% of the time, 63% of requests hit a slow one.
  • Hedged requests: send a second copy after the p95 time. Take the first answer.
  • Set timeouts and budgets per hop. Drop work that will miss the deadline.
At scale, p99 becomes the median.

L5

Hardcore

Prove it, break it, read the papers. New problem: bugs hide in event orders you will never see in normal testing.

0 / 10 done

FLP impossibility

  • In a fully asynchronous network, no deterministic algorithm can always reach consensus if even one node may crash.
  • Reason: you cannot tell a dead node from a slow one.
  • Real systems give up a little. They stay safe always and make progress when the network behaves.
Safety always. Liveness when lucky.

Paxos

  • The original consensus protocol (Lamport). Raft is a cleaner relative.
  • Phase 1: proposer sends Prepare(n). Acceptors promise to ignore lower numbers.
  • Phase 2: proposer sends Accept(n, v). A majority accepting = value chosen.
  • Key rule: if any acceptor already accepted a value, the proposer must reuse it.
  • Family: Multi-Paxos, Viewstamped Replication, EPaxos, Flexible Paxos.

Byzantine faults

  • Crash faults stop. Byzantine faults lie: they send different values to different nodes.
  • To survive f liars you need n ≥ 3f + 1 nodes. 4 nodes survive 1 liar.
  • Protocols: PBFT, Tendermint, HotStuff. Blockchains live here.
  • Inside one company's data center, most systems assume crash faults only.

CRDTs

  • Data types that merge without coordination. No locks, no leader.
  • The merge is commutative, associative and idempotent. Order and repeats do not matter.
  • G-counter: one slot per replica. Merge = max of each slot. Value = sum.
  • Used for offline-first apps and collaborative editors (Automerge, Yjs), and Riak.
Strong eventual consistency: same updates seen = same state.

Metastable failures

  • A short trigger pushes the system into a bad state. The trigger ends. The outage does not.
  • Usual loop: retries add load, load adds latency, latency adds retries.
  • Fixes: exponential backoff with jitter, retry budgets, circuit breakers, load shedding.
  • Under overload, serve fewer requests well instead of all requests badly.
Retries are load. Budget them.

Cells and blast radius

  • Split the system into full, independent copies called cells.
  • Each customer lives in one cell. A thin router sends them there.
  • A bad deploy, a poison request or a hot tenant hurts one cell only.
  • Shuffle sharding gives each customer a random set of nodes, so two customers rarely share all of them.

Deterministic simulation testing

  • Run the whole cluster in one thread, with a fake network, disk and clock.
  • A random seed drives every choice: delays, drops, crashes, message order.
  • A failing seed replays the exact same bug every time.
  • FoundationDB built its database this way. TigerBeetle and Antithesis use it today.
Turn "can't reproduce" into a seed number.

Jepsen and history checking

  • Jepsen tests real databases from the outside, like a black box.
  • Clients run operations. A "nemesis" cuts the network, skews clocks and kills nodes.
  • A checker reads the recorded history and asks: could any legal order produce this?
  • It has found data loss in many popular databases. Read the reports at jepsen.io.

Formal methods (TLA+)

  • Write the design as a spec: states, actions, and rules that must always hold.
  • A model checker tries every order of steps in a small model.
  • It finds bugs that need 20+ precise steps. Humans miss those.
  • AWS reported using TLA+ on DynamoDB, S3 and other core systems.
Test the design before you write the code.
