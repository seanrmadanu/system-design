Basics

One server, then a few. New problem: one machine can't handle the traffic.

What system design is

  • You turn a fuzzy goal into parts (boxes) and data paths (arrows).
  • Functional needs: what it does. "Users post photos."
  • Non-functional needs: how well. Latency, uptime, scale, cost.
  • No design is "right". Every choice trades one thing for another.
Rule: say the trade-off out loud.
Real case Twitter2008–2013

What happened

Twitter ran as one Ruby on Rails app on MySQL. Traffic spikes, like the 2010 World Cup, kept taking it down, and users saw the "Fail Whale" error page.

The fix

Twitter rebuilt the system as many separate services on the JVM. In 2013 it handled a record 143,199 tweets in one second with no problems.

Source: Twitter engineering blog

Life of a request

  • DNS turns a name into an IP address.
  • TCP + TLS open a safe connection. This costs round trips.
  • HTTP carries the request. The server answers with a status code.
  • The server usually calls a database before it answers.
Every arrow here adds latency.
Real case Facebook (Meta)2021

What happened

A maintenance command cut every link in Facebook's backbone network. Its DNS servers then withdrew their BGP routes, so nobody could look up facebook.com. Facebook, Instagram and WhatsApp were down for about 6 hours.

The fix

Engineers went into the data centers in person to bring the network back. Meta then committed to stronger safety checks, testing and recovery drills.

Source: Meta engineering blog

Latency numbers

  • Memory is about 1,000× faster than SSD.
  • A round trip inside one data center is cheap. A trip across an ocean is not.
  • Most design moves exist to swap a slow step for a fast one.
Cache in RAM. Keep data close to users.
Real case Google2009

What happened

In a test, Google added 100–400 ms of delay to search results. Users searched 0.2–0.6% less, and some kept searching less even after the delay was gone.

The fix

Google made speed a core goal. It later built SPDY and QUIC, which became HTTP/2 and HTTP/3, to cut network round trips.

Source: Google Research blog

Back-of-envelope math

  • Estimate load before you pick parts.
  • Round hard. 86,400 seconds a day ≈ 100k.
  • Peak traffic is often 2–5× the average.
10M users × 10 req = 100M req/day 100M ÷ 100k s = ~1,000 req/s avg peak ≈ 3 × avg = ~3,000 req/s 1 KB × 100M = 100 GB/day stored 100 GB × 365 = ~36 TB/year
Real case Niantic + Google Cloud (Pokémon GO)2016

What happened

Niantic planned for 1× traffic, with 5× as the worst case. Real traffic hit 50× the plan, which was 10× the worst case.

The fix

Google's reliability team added tens of thousands of CPU cores, upgraded the GKE cluster to add 1,000+ more nodes, and moved to a global HTTPS load balancer.

Source: Google Cloud blog

Vertical vs horizontal scaling

  • Vertical: buy a bigger machine. Simple. Has a ceiling. One failure takes all.
  • Horizontal: add more machines. No ceiling. Needs a load balancer.
  • Horizontal works best when servers are stateless. Keep sessions in a shared store.
Stateless app servers + shared state store.
Real case Netflix2008

What happened

A major database corruption in Netflix's own data center stopped DVD shipping for three days. One big, vertically scaled database was a single point of failure.

The fix

Netflix moved to horizontally scaled, distributed systems in the AWS cloud. The move finished in 2016.

Source: Netflix newsroom

Load balancer

  • Spreads requests across servers.
  • Algorithms: round robin, least connections, hash by user or IP.
  • Health checks remove dead servers from the pool.
  • L4 routes by IP and port. L7 reads HTTP and routes by path or header.
  • Run two balancers, or the balancer becomes the new single point of failure.
Real case AWS + Netflix2012

What happened

On Christmas Eve, a maintenance process ran against production by mistake and deleted state data for AWS Elastic Load Balancing (ELB). Many load balancers broke, and Netflix streaming failed for many users.

The fix

AWS locked that data behind a change-approval step and improved its recovery process. Netflix started running in two regions (see Multi-region in L4).

Source: AWS post-event summary

Caching

  • Keep hot data in RAM (Redis, Memcached). Skip the slow database.
  • Cache-aside: app checks cache, then DB on a miss, then fills the cache.
  • TTL expires old entries. LRU evicts the least recently used when full.
  • Hard part: stale data. When the DB changes, delete or update the cache entry.
Hit rate is the number that matters.
Real case Twitter2012

What happened

Building a home timeline on request meant reading recent tweets from everyone a user follows. At Twitter's size this was far too slow.

The fix

When someone tweets, Twitter writes the tweet ID into each follower's timeline list in a Redis cache. Reading a timeline becomes one fast cache read.

Source: Timelines at Scale talk (InfoQ)

CDN

  • A CDN is a cache for files, placed in many cities.
  • Images, video, JS and CSS load from the nearest edge.
  • The edge calls your origin server only on a miss.
  • Result: lower latency and much less load on your servers.
Real case Fastly2021

What happened

A bug shipped on May 12 waited for one rare setting. On June 8, a customer pushed a valid config that triggered it. 85% of Fastly's network returned errors, and big sites like Reddit and major news sites went down.

The fix

Fastly saw it within 1 minute and turned off that customer setting. 95% of the network was normal again within 49 minutes, and a permanent fix rolled out the same day.

Source: Fastly blog

SQL vs NoSQL

  • SQL: tables, joins, ACID transactions. Postgres, MySQL.
  • NoSQL: key-value, document, wide-column, graph. Built for one access pattern at large scale.
  • Pick by access pattern, not by hype.
Default: Postgres. Switch only for a clear reason.
Real case Discord2015–2022

What happened

Discord stored messages in MongoDB, then moved to Cassandra in 2017. By 2022, 177 Cassandra nodes suffered hot partitions, garbage-collection pauses and slow compaction.

The fix

Discord moved to ScyllaDB, which has no garbage collector, and added Rust data services that merge duplicate reads. 72 nodes now do the job, and p99 read latency fell from 40–125 ms to 15 ms.

Source: Discord blog

Real case Facebook (Meta)2012

What happened

Facebook's new native iOS app needed News Feed data. REST endpoints sent too much or too little data, so the app made many round trips.

The fix

Facebook created GraphQL. The app asks for exactly the fields it needs in one request. Facebook made it open source in 2015.

Source: Meta engineering blog

Mid

Scale the data, not only the servers. New problem: the database is now the bottleneck.

Replication

  • Keep copies of the same data on several machines.
  • Leader–follower: writes go to the leader. Followers copy it and serve reads.
  • Replication lag: a follower can be behind. You may read old data.
  • Failover: if the leader dies, promote a follower.
Scales reads. Does not scale writes.
Real case GitHub2018

What happened

A 43-second network split cut off GitHub's main East Coast data center. The failover tool (Orchestrator) promoted West Coast databases, so each coast then held writes the other did not have.

The fix

GitHub ran degraded for 24 hours and 11 minutes while it restored data and replayed the missing writes. It then blocked automatic database failover across regions.

Source: GitHub blog

Sharding

  • Split data across machines. Each shard holds a slice.
  • Hash sharding: even spread. Range queries get hard.
  • Range sharding: easy ranges. Risk of hot shards.
  • Hot key: one celebrity account can overload one shard.
  • Cross-shard joins and transactions get slow. Pick the shard key with care.
Scales writes. Costs joins.
Real case Instagram (Meta)2011

What happened

Instagram's data outgrew a single PostgreSQL server.

The fix

Instagram split data into thousands of logical shards, mapped onto far fewer physical servers. Each ID packs 41 bits of time, 13 bits of shard ID and 10 bits of sequence, so IDs are unique and sort by time.

Source: Instagram engineering blog

Consistent hashing

  • Put nodes and keys on one ring.
  • A key belongs to the next node clockwise.
  • Add or remove a node: only its neighbor's keys move. About 1/N of keys.
  • Virtual nodes: each server takes many ring spots. Load evens out.
  • Used in DynamoDB, Cassandra, CDNs, cache clusters.
Real case Vimeo2016

What happened

Vimeo sent video requests to cache servers with consistent hashing. Popular videos overloaded some servers while others sat idle.

The fix

Vimeo added "consistent hashing with bounded loads", a 2016 Google research idea, to HAProxy. No server may take much more than the average load. Cache bandwidth fell to about one eighth.

Source: Google Research blog

CAP theorem

  • Networks split. When they do, a node must choose.
  • CP: refuse to answer. Never wrong, sometimes down.
  • AP: answer with what it has. Always up, sometimes stale.
  • PACELC: with no split, you still trade latency (L) for consistency (C).
Banks lean CP. Like counters lean AP.
Real case Amazon2007

What happened

Amazon's shopping cart must accept "Add to cart" even during network splits and server failures. A rejected add is a lost sale.

The fix

Amazon built Dynamo, an AP key-value store. It always accepts writes and merges conflicting cart versions later. The trade-off: a deleted item can sometimes come back.

Source: All Things Distributed (Werner Vogels)

Message queues

  • Producers drop jobs in a queue. Workers pull them later.
  • Absorbs traffic spikes. The web request returns fast.
  • Decouples services. A slow worker does not block users.
  • Failed jobs retry, then go to a dead-letter queue.
  • Tools: SQS, RabbitMQ, Kafka.
Real case Slack2016–2017

What happened

Slack's job queue ran on Redis. A database slowdown made jobs pile up until Redis ran out of memory. Slack could no longer add or remove jobs, and the queue stayed stuck after the database recovered.

The fix

Slack put Kafka in front of Redis. Kafka keeps jobs safely on disk during a backlog, and a relay feeds them into Redis at a safe rate.

Source: Slack engineering blog

Stampede: a hot key expires and thousands of requests hit the DB at once. Fix it with a lock, early refresh, or random TTLs.

Real case Facebook (Meta)2013

What happened

When a popular cache key was deleted, many servers missed at once and hit the database together. Late writes also put stale values back into the cache.

The fix

Memcache "leases": only one client gets a token to refill a missing key, and the others wait briefly. This cut peak database reads from about 17,000 to 1,300 per second.

Source: Scaling Memcache at Facebook (paper)

Rate limiting

  • Caps requests per user, IP or API key.
  • Token bucket: tokens refill at a fixed rate. Each request takes one. Empty bucket means HTTP 429.
  • Bucket size sets the allowed burst.
  • Other options: fixed window, sliding window log, leaky bucket.
  • Shared limits across servers need a shared counter, often Redis.
Real case Stripe2017

What happened

One user's runaway script, or a burst of retries on slow endpoints, could overload Stripe's payments API for everyone.

The fix

Stripe added four layers: a token bucket per user, a cap on requests in progress, and two load shedders that keep capacity for critical calls like charges. The limits run on Redis.

Source: Stripe blog

Indexes

  • No index: the DB scans every row. 10M rows = slow.
  • B-tree index: 3–4 page reads find one row.
  • Each index speeds reads but slows writes and uses disk.
  • Composite index (a, b) helps queries on a, or a + b. Not b alone.
Index the columns in your WHERE and ORDER BY.
Real case Uber2016

What happened

In PostgreSQL, updating a row writes a new copy of the row, and the table's indexes must point to it. Uber's write-heavy tables caused heavy extra writes and replication traffic.

The fix

Uber moved to MySQL with InnoDB. Its secondary indexes point to the primary key, so an update only touches indexes on the columns that changed.

Source: Uber engineering blog

Monolith vs microservices

  • Monolith: one codebase, one deploy. Fast to start.
  • Microservices: small services, each with its own data. Teams ship alone.
  • Cost: network calls, partial failures, harder debugging.
  • An API gateway handles auth, routing and rate limits at the front door.
Start with a monolith. Split when teams block each other.
Real case Uber2020

What happened

Uber grew to about 2,200 critical microservices. One feature could need changes in many services, and tracing a failure across them was slow.

The fix

Uber grouped services into domains, each behind one gateway, and sorted domains into layers. Teams now call a domain's gateway instead of dozens of services. Uber calls this DOMA.

Source: Uber engineering blog

Interview framework

  • Ask before you draw. Who uses it? How many? Read-heavy or write-heavy?
  • Do quick math. It tells you which parts matter.
  • Draw a simple design that works. Then fix the bottleneck.
  • Close with trade-offs and what you would do next.
Real case HealthCare.gov (US government)2013

What happened

The site launched with little load testing or end-to-end testing. It crashed on day one under more users than it could handle, and very few people could sign up.

The fix

A small "tech surge" team, including Google site reliability engineers, added monitoring and fixed the bottlenecks one by one. The site worked by December, and the team led to the US Digital Service.

Source: Wikipedia

Advanced

Look inside the data systems. New problem: copies disagree, retries double-charge, writes get lost.

Storage engines: B-tree vs LSM

  • B-tree: updates pages in place. Fast reads. Postgres, MySQL.
  • LSM-tree: appends only. Fast writes. RocksDB, Cassandra.
  • LSM writes go to a log and a RAM table, then flush to sorted files.
  • Background compaction merges files and drops old versions.
  • Bloom filters let reads skip files that cannot hold the key.
Write-heavy? LSM. Read-heavy? B-tree.
Real case Facebook (Meta)2016

What happened

Facebook's main user database (UDB) ran MySQL on InnoDB, a B-tree engine. It used a lot of flash storage and wrote too much to the flash drives.

The fix

Facebook built MyRocks: MySQL on RocksDB, an LSM-tree engine. It used about half the storage of compressed InnoDB and wrote much less to flash.

Source: Meta engineering blog

Consistency models

  • A consistency model is a promise about what reads can return.
  • Stronger promise = more coordination = more latency.
  • Many apps need only read-your-writes for the user's own data.
  • Pick per feature. A bank balance and a like counter need different promises.
Real case Amazon S32020

What happened

For 14 years, S3 was only eventually consistent for overwrites, deletes and listings. An app that read right after a write could see old data, so many teams built their own workarounds.

The fix

In December 2020, S3 became strongly consistent (read-after-write) for every operation, at no extra cost and with no code changes.

Source: AWS News Blog

Quorums

  • N copies. A write waits for W acks. A read asks R copies.
  • If W + R > N, every read set overlaps every write set.
  • The overlap copy holds the newest version. The reader keeps the newest.
  • Common setting: N=3, W=2, R=2. Survives one dead node.
  • Used in Dynamo-style stores: Cassandra, Riak, DynamoDB internals.
Real case Amazon Aurora2017

What happened

With 3 copies and a 2-of-3 quorum, losing one AZ plus one more disk breaks the quorum. In a huge fleet, that second failure is not rare.

The fix

Aurora keeps 6 copies across 3 AZs. Writes need 4 and reads need 3. It keeps writing after losing a whole AZ, and loses no data after losing an AZ plus one more copy.

Source: AWS Database blog

Many databases default to read committed. Check yours. Fix lost updates with atomic updates (SET n = n + 1), SELECT … FOR UPDATE, or serializable mode.

Real case Flexcoin + Poloniex (bitcoin exchanges)2014

What happened

Attackers sent thousands of withdrawal requests at once. Each passed the balance check before any debit was saved, so balances went negative. Flexcoin lost about 896 bitcoin and shut down. Poloniex lost about 12% of its bitcoin.

The fix

The safe pattern: check and debit in one transaction with a row lock (SELECT … FOR UPDATE) or serializable isolation. A 2017 study, ACIDRain, found 22 bugs like this in popular online-shop software.

Source: Computerworld

Two-phase commit (2PC)

  • One transaction across two databases. All commit or none.
  • Phase 1: coordinator asks "can you commit?" Each node locks and votes.
  • Phase 2: all YES → commit. Any NO → abort.
  • Weak spot: a dead coordinator leaves nodes stuck, holding locks.
Correct, but slow and blocking.
Real case Google2010

What happened

Google rebuilt its search index with huge batch MapReduce jobs. A new page waited for the next full run, so the index was often days old.

The fix

Google built Percolator: small transactions on Bigtable, made atomic with two-phase commit, that update the index one page at a time. The average age of documents in search results fell by 50%.

Source: Google Research (Percolator paper)

Sagas

  • Split a long process into local steps. Each step commits alone.
  • If a step fails, run compensating steps in reverse.
  • No global locks. Other users can see half-done states.
  • Orchestrated: one service drives the steps. Choreographed: services react to events.
Microservices use sagas, not 2PC.
Real case Uber2017–2023

What happened

Uber's business flows, like trips and payments, span many services. Hand-written retries and queues for each step were fragile and hard to debug.

The fix

Uber built Cadence, a workflow engine. It saves each step's progress, retries failed steps, and lets code run undo steps when a later step fails. Over 1,000 Uber services use it.

Source: Uber engineering blog

Event logs (Kafka)

  • A topic is an append-only log, split into partitions.
  • Events keep their order inside one partition only. Key by user or order ID.
  • Each consumer group tracks its own offset. Many readers, one log.
  • Events stay for days. A new service can replay history.
Queue: a job is done once. Log: events are kept and replayed.
Real case LinkedIn2010–2011

What happened

LinkedIn had many custom pipelines moving data between databases, search, analytics and monitoring. Every new system needed new links to all the others.

The fix

LinkedIn built Kafka: one central, replayable log of events that every system writes to and reads from. It became open source in 2011.

Source: Wikipedia: Apache Kafka

Idempotency

  • Networks drop replies. Clients retry. Retries can repeat side effects.
  • An idempotent operation gives the same result if run twice.
  • Client sends a unique idempotency key. Server stores key + result.
  • "Exactly once" in practice = at-least-once delivery + dedupe.
Every payment API needs this.
Real case Stripe2017

What happened

A payment request can time out after the charge already went through. If the client simply retries, the customer pays twice.

The fix

Stripe's API takes an Idempotency-Key header. The server saves the first result for that key and returns it for every retry, so the charge happens once.

Source: Stripe blog

Outbox pattern and CDC

  • Dual-write bug: save to DB, then publish to Kafka. If step 2 fails, systems drift.
  • Outbox: write the row and the event in one DB transaction.
  • A relay reads the outbox table and publishes. It retries until it succeeds.
  • CDC (change data capture) reads the DB's own log. Tool: Debezium.
Real case Netflix2019–2020

What happened

Netflix services wrote to a database and to other stores, like search indexes, in separate steps. When one write failed, the copies drifted apart.

The fix

Netflix built DBLog, a CDC tool. It reads the database's own change log and streams every change out, so other systems update from one source of truth.

Source: DBLog paper (arXiv)

Observability and SLOs

  • Metrics tell you something is wrong. Traces show where. Logs show why.
  • SLI: what you measure, like p99 latency. SLO: the target. Error budget: allowed failure.
  • Watch p99, not the average. Averages hide slow users.

Real case Google2016

What happened

Developers wanted to ship fast. Operations teams wanted stability. Every launch turned into an argument.

The fix

Google's SRE teams set an SLO for each service. The gap between 100% and the SLO is the error budget. While budget remains, teams ship. When it runs out, launches pause.

Source: Google SRE book

Expert

Distributed systems theory. New problem: clocks drift, messages vanish, and nodes stop in the middle of a step.

Partial failure

  • One machine either works or crashes. A cluster can be half broken.
  • A timeout tells you nothing about the cause.
  • Failure models: crash-stop, crash-recovery, lost messages, slow nodes, lying nodes (Byzantine).
  • The network is not reliable, latency is not zero, and clocks are not in sync.
Design every call for "no answer".
Real case Slack2021

What happened

On January 4, an AWS Transit Gateway could not scale fast enough for post-holiday traffic and dropped packets. Healthy web servers looked dead because their calls were slow. Automation removed them and tried to add about 1,200 servers, which overloaded the provisioning service.

The fix

AWS raised gateway capacity by hand. Slack moved its dashboards off that gateway, load-tests provisioning regularly, and reviewed its health checks and autoscaling.

Source: Slack engineering blog

Logical clocks

  • Wall clocks drift. NTP can jump them backward. "Last write wins" by timestamp can drop writes.
  • Lamport clock: a counter. +1 per event. On receive: max(mine, message) + 1.
  • If a caused b, then L(a) < L(b). The reverse is not true.
  • Vector clocks keep one counter per node. They detect concurrent events.
Real case Cloudflare2017

What happened

On January 1, a leap second made the clock step back. Cloudflare's DNS code, written in Go, measured a round trip as a negative time. A random-number call then failed on the negative value, and some DNS lookups failed.

The fix

Cloudflare discarded negative measurements and patched the worst machines within 90 minutes. The lesson: measure time spans with a monotonic clock, never with wall-clock time.

Source: Cloudflare blog

Linearizability

  • The system acts like one copy. Once a write finishes, every later read sees it.
  • Needed for locks, leader election, unique usernames, bank balances.
  • Linearizable is about one object in real time. Serializable is about transactions over many objects.
  • Both together = "strict serializable". Spanner gives this.
Real case MongoDB2015–2017

What happened

Jepsen tests in 2015 showed MongoDB could return stale and even uncommitted data, even with majority writes. A read right after a write could miss it.

The fix

MongoDB 3.4 added a new replication protocol and a "linearizable" read concern. Jepsen's 2017 tests found it passed linearizability checks.

Source: Jepsen analysis

Consensus: Raft leader election

  • Consensus = nodes agree on one value, even when some crash.
  • Raft picks one leader per term. Terms only go up.
  • A follower that hears no heartbeat becomes a candidate and asks for votes.
  • Majority wins. 5 nodes survive 2 failures. 3 nodes survive 1.
  • Built on it: etcd, Consul, CockroachDB, Kafka KRaft.
Real case Roblox2021

What happened

Roblox ran its core services on HashiCorp Consul, which uses Raft. Under heavy load, a new streaming feature and a slowly growing storage file (BoltDB) made Consul leaders very slow. Roblox was down for 73 hours.

The fix

Roblox turned off streaming, compacted the database, split critical services into separate Consul clusters, and built a second data center.

Source: Roblox newsroom

Consensus: Raft log replication

  • The leader appends each command to its log and sends it to followers.
  • An entry is committed when a majority stores it.
  • Committed entries never change. All nodes apply them in the same order.
  • Same log + same order = same state machine. This is state machine replication.
Real case Apache Kafka2019–2025

What happened

Kafka kept its cluster metadata in a separate ZooKeeper cluster. That limited how many partitions a cluster could hold and made controller failover slow.

The fix

KIP-500 moved the metadata into Kafka itself, as a Raft-replicated log called KRaft. Kafka 4.0 (2025) removed ZooKeeper completely.

Source: KIP-500 (Apache wiki)

Split brain and fencing tokens

  • A lock holder can pause (GC, VM freeze) and wake up after its lease expired.
  • It still thinks it holds the lock. Now two nodes act as leader.
  • Fix: the lock service hands out a number that always goes up, the fencing token.
  • Storage rejects any write with a token older than one it has seen.
Leases alone are not safe. Fence the writes.
Real case Google2006

What happened

In Google's Chubby lock service, a client could be paused or delayed, lose its lock, and still send old requests as if it held the lock.

The fix

Chubby hands out "sequencers": tokens that carry the lock's generation number. Servers check the token and reject stale ones. This is the same idea as a fencing token.

Source: Google Research (Chubby paper)

TrueTime and Spanner

  • Google Spanner is a global SQL database with strict serializability.
  • TrueTime uses GPS and atomic clocks. It returns a time range, not one point.
  • On commit, Spanner picks the top of the range, then waits out the uncertainty.
  • After the wait, any later transaction gets a larger timestamp. Order is safe without talking.
Spend a few ms of waiting to buy global order.
Real case Google2012

What happened

Google's ads business (AdWords) ran on MySQL split into shards by hand. Resharding was risky and slow, and transactions across shards were hard.

The fix

Google built F1, a SQL database on top of Spanner. Spanner uses TrueTime for globally ordered transactions and moves data between servers automatically.

Source: Google Research (F1 paper)

Multi-region

  • Active–passive: one region writes, one waits. Simple. Failover can lose the last seconds.
  • Active–active: both regions write. Low latency everywhere. Conflicts appear.
  • Conflict fixes: last-write-wins, merge rules, CRDTs, or one "home region" per user.
  • A sync write across an ocean adds about 100 ms or more.
Real case Netflix2013

What happened

The Christmas Eve 2012 load balancer outage hit only one AWS region, yet Netflix went down. One region was a single point of failure.

The fix

Netflix ran its service active–active in two AWS regions, with Cassandra copying data between them. If one region fails, traffic moves to the other.

Source: Netflix tech blog

Tail latency at scale

  • One user request may fan out to 100 servers. It is as slow as the slowest one.
  • If each server is slow 1% of the time, 63% of requests hit a slow one.
  • Hedged requests: send a second copy after the p95 time. Take the first answer.
  • Set timeouts and budgets per hop. Drop work that will miss the deadline.
At scale, p99 becomes the median.
Real case Google2013

What happened

In a test that read 1,000 keys spread over 100 Bigtable servers, the slowest replies set the total time. The 99.9th percentile was 1,800 ms.

The fix

Hedged requests: if a reply takes more than 10 ms, send a copy to another server and use whichever answers first. The 99.9th percentile fell to 74 ms with only about 2% more requests.

Source: Google Research (The Tail at Scale)

FLP impossibility

  • In a fully asynchronous network, no deterministic algorithm can always reach consensus if even one node may crash.
  • Reason: you cannot tell a dead node from a slow one.
  • Real systems give up a little. They stay safe always and make progress when the network behaves.
Safety always. Liveness when lucky.
Real case Elastic (Elasticsearch)2019

What happened

Older Elasticsearch needed a hand-set "minimum master nodes" number. A wrong value let a network split elect two masters (split brain), and data could be lost.

The fix

Elasticsearch 7.0 replaced it with a new coordination system that works out quorums by itself and was checked with TLA+. With no majority, the cluster waits instead of electing two leaders.

Source: Elastic blog

Paxos

  • The original consensus protocol (Lamport). Raft is a cleaner relative.
  • Phase 1: proposer sends Prepare(n). Acceptors promise to ignore lower numbers.
  • Phase 2: proposer sends Accept(n, v). A majority accepting = value chosen.
  • Key rule: if any acceptor already accepted a value, the proposer must reuse it.
  • Family: Multi-Paxos, Viewstamped Replication, EPaxos, Flexible Paxos.
Real case Google2007

What happened

Google rebuilt the database under its Chubby lock service on Paxos. The algorithm fit on one page, but the real system had to handle disk corruption, leader changes and changes to the set of servers.

The fix

The team added master leases, snapshots, checksums and heavy random fault-injection tests. Their paper, "Paxos Made Live", explains the gap between theory and production.

Source: Google Research (Paxos Made Live)

Byzantine faults

  • Crash faults stop. Byzantine faults lie: they send different values to different nodes.
  • To survive f liars you need n ≥ 3f + 1 nodes. 4 nodes survive 1 liar.
  • Protocols: PBFT, Tendermint, HotStuff. Blockchains live here.
  • Inside one company's data center, most systems assume crash faults only.
Real case Cloudflare2020

What happened

A network switch failed only partly. Two etcd nodes saw the network differently, so leader elections tied again and again, and the cluster could not accept writes. Knock-on database failovers hurt Cloudflare's API and dashboard for over 6 hours.

The fix

Cloudflare fixed a bug that forced replica rebuilds after a failover and made automatic database promotion less eager. Cloudflare called it a Byzantine failure. Experts later said an "omission fault" describes it better.

Source: Cloudflare blog

CRDTs

  • Data types that merge without coordination. No locks, no leader.
  • The merge is commutative, associative and idempotent. Order and repeats do not matter.
  • G-counter: one slot per replica. Merge = max of each slot. Value = sum.
  • Used for offline-first apps and collaborative editors (Automerge, Yjs), and Riak.
Strong eventual consistency: same updates seen = same state.
Real case Figma2019

What happened

Figma needed many people to edit one design file at the same time, with every change showing up instantly for everyone.

The fix

Figma borrowed CRDT ideas, like last-writer-wins for each property, but kept a central server as the final authority. That was simpler than a fully decentralized CRDT.

Source: Figma blog

Metastable failures

  • A short trigger pushes the system into a bad state. The trigger ends. The outage does not.
  • Usual loop: retries add load, load adds latency, latency adds retries.
  • Fixes: exponential backoff with jitter, retry budgets, circuit breakers, load shedding.
  • Under overload, serve fewer requests well instead of all requests badly.
Retries are load. Budget them.
Real case Amazon DynamoDB2015

What happened

Storage servers asked a metadata service for their partition lists. Bigger lists, from new secondary indexes, plus a short network blip made requests time out. The servers retried, which kept the service overloaded. Errors reached about 55%.

The fix

AWS paused requests to the metadata service to stop the retry storm, then added capacity. Later it split the metadata service into separate instances and watched list sizes.

Source: AWS post-event summary

Cells and blast radius

  • Split the system into full, independent copies called cells.
  • Each customer lives in one cell. A thin router sends them there.
  • A bad deploy, a poison request or a hot tenant hurts one cell only.
  • Shuffle sharding gives each customer a random set of nodes, so two customers rarely share all of them.
Real case Slack2021–2023

What happened

On June 30, 2021, a network link to one AWS AZ kept failing on and off. Parts of the system disagreed about which servers were healthy, so the spare AZs did not contain the problem.

The fix

Slack turned each AZ into a cell. Services only talk to servers in their own AZ, and operators can drain traffic away from a bad AZ within minutes.

Source: Slack engineering blog

Deterministic simulation testing

  • Run the whole cluster in one thread, with a fake network, disk and clock.
  • A random seed drives every choice: delays, drops, crashes, message order.
  • A failing seed replays the exact same bug every time.
  • FoundationDB built its database this way. TigerBeetle and Antithesis use it today.
Turn "can't reproduce" into a seed number.
Real case FoundationDB (Apple)2009–2015

What happened

Bugs in distributed databases show up only in rare orders of events. Normal tests almost never hit them, and they are nearly impossible to reproduce.

The fix

FoundationDB built a deterministic simulator first, then the database. It runs whole clusters with injected faults, and any failure replays exactly from its seed. Apple bought FoundationDB in 2015 and uses it for iCloud.

Source: FoundationDB docs

Jepsen and history checking

  • Jepsen tests real databases from the outside, like a black box.
  • Clients run operations. A "nemesis" cuts the network, skews clocks and kills nodes.
  • A checker reads the recorded history and asks: could any legal order produce this?
  • It has found data loss in many popular databases. Read the reports at jepsen.io.
Real case MongoDB2020

What happened

Jepsen tested MongoDB 4.2.6 transactions. Under default settings, acknowledged writes were lost during network splits. Even the strongest settings showed anomalies such as read skew.

The fix

MongoDB found a bug in its transaction retry code and fixed it in 4.2.8. Jepsen advised setting read and write concerns on every transaction.

Source: Jepsen analysis

Formal methods (TLA+)

  • Write the design as a spec: states, actions, and rules that must always hold.
  • A model checker tries every order of steps in a small model.
  • It finds bugs that need 20+ precise steps. Humans miss those.
  • AWS reported using TLA+ on DynamoDB, S3 and other core systems.
Test the design before you write the code.
Real case Amazon Web Services2011–2015

What happened

Some of the worst bugs are design bugs. They need a rare order of failures and recoveries, so normal testing misses them.

The fix

AWS engineers wrote TLA+ specs for DynamoDB, S3 and other services. The model checker found a data-loss bug in DynamoDB replication whose shortest trace was 35 steps long.

Source: Amazon Science
